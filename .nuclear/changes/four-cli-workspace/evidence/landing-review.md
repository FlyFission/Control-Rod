| L3 | P1 | Linux checkers saw the host credential read-only, so a sign-in refreshed during a check could not be saved. | Three designs were reviewed. Read-only (#134 as written) makes a Codex check exit with no verdict when it must refresh. A private copy (round 2) keeps the host file intact but, with token rotation, leaves the host holding a dead token after one refreshing check, and a copy can outlive a crashed daemon. Landing keeps **main's writability**: the login directory is read-only and only the credential file is writable. What #134 adds, and this PR keeps, is for Codex on Linux only: `CODEX_HOME` points at a new per-run directory (0700, under the run's disposable login parent, removed with the run) so Codex's app-server and SQLite state can be written without the host login directory becoming writable; the same host credential file is bound writable inside it (a second path to the one file main already makes writable, nothing more); and scratch gets a tmpfs so Codex's nested linux-sandbox can create its mount points without them reaching the host. Narrowing credential custody further (a daemon write-back, or a checker UID of its own) is left to a separate change for the owner. Test `TestCheckerMountKeepsTheLoginDirectoryReadOnlyAndSavesARefreshedCredential` checks that the login directory has no writable bind, that the credential is bound writable, and that a token written inside the sandbox reaches the host file. It needs Bubblewrap, so it runs in CI. Not tested: a live OAuth refresh, and whether a CLI that saves by renaming over the file can write through a file bind. |
| L4 | P2 | Promotion bound a workspace project only when `[project-id:]` came right after `[mode:]`, while intake's workflow choice read it anywhere on the header line. | Fixed: promotion reads `project-id` from the same top-level tags, and refuses a header that names two. Test: "binds a workspace project whatever the order of the header's tags". Round 2: when a header names both a project and a different workspace id, intake's workflow choice now follows the id too (`captureProject`), and an exact id wins over another project whose name equals that id, so both steps agree. |
