# Review: Control Rod workbench ontology and buildout (2026-10-29)

## Verdict

The ontology itself is genuinely strong: the identity versus observation split, mutability classes, link table and interface layer map cleanly onto the real schema, and most claims about the existing kernel, contracts and UI checked out exactly against source. But the package is not yet trustworthy in its details. I found one protected-surface impact assessment that is flatly wrong (attempt sets cannot run under the current kernel lifecycle), a rigor table that reads as weakening the kernel's pre-check floor, several claims about existing code that are false (draft-edit CAS being the worst, since it documents a control that does not exist), and a fully specified Baseline object with no implementation task and no acceptance gate. Fix the false claims, the action catalog's exhaustiveness, and the attempt-set kernel routing before this goes to the owner for D-1 to D-6 sign-off.

## What the design gets notably right

1. The ground-truth discipline is real: every kernel fact I checked (Status and Action enums, ActorKind, the independence and override rules, ReasonCode), every contract fact (DataLane, RigorMode, CouplingProfile's five axes, RunStatus), and even the experience claims (DecisionBar returns null at `DecisionBar.tsx:33`, raw log lines in `RunLog.tsx:150-152`, the README's "runs in a sandbox" sentence, the roughly 1,900 line React surface) verified against source.
2. Identity versus observation with explicit mutability classes is cleanly modelled and honestly applied (Run versus ExecutionTrace, append-only Event, frozen revisions), which is the part most ontology efforts get wrong.
3. ActionDescriptor and AttentionItem as specified projections make refusals teach and structurally guarantee the decision bar cannot silently vanish, fixing a verified defect class rather than decorating it.
4. The donor register is exemplary: pinned commits, file-level license rechecks, an explicit what-to-leave list naming the trust gaps being refused, and ADR 0019's clean-room conditions carried into a gated task (0.4).
5. The freeze as the single bridge from live exploration to the headless promise path (N-5, plus "controlled runs cannot be typed into") admits live sessions without weakening the frozen, passkey-signed accept path that makes the product worth building.

## Questions I could not resolve

- Does the owner have a macOS host for spike S-1? WB-15 gates on passing "on macOS and WSL2"; packet E-03 observes only WSL2, while `docs/patterns/kandev.md` references "Ben's first real run on his Mac". If there is no Mac, the WB-15 gate cannot be met as written.
- Is the Administrative rigor row intended to allow acceptance with no independent pre-check (a protected kernel change), or is the row simply misworded? The answer decides whether R-02 is a design flaw or a documentation bug.
- How are attempt-set candidates meant to map onto Run rows (new role, candidate index, reused rounds) given the live-run index and MAX_ROUNDS equal to 3?
- At what scope is a Baseline "current" (per package, per project, per deliverable), and which component observes deadband crossings to mark it stale?
- The plan's definition of done references "a fresh version of `docs/owner-pilot.md`", which is not present in the provided copy (the copy's `docs/` tree is partial: no README, threat model or sqa directory). I could not tell whether this is a stale reference or an artefact of the partial copy.
- The universal donor claim ("Every one lets authority outrun evidence somewhere") is substantiated by category in the register but not itemized per donor; the per-donor mapping lives in working papers outside the repository, so I could not verify all eighteen.
- The basis pins (`06446bf` on `claude/magical-ritchie-e7t851`, PR #11 on #6) cannot be verified from a source copy without git metadata.
