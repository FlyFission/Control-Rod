1. **[P1] Proof exports disclose unrelated organizations’ and lanes’ event bodies.** [seals.ts:185](/home/flyfission/worktrees/control-rod-p5records/services/api/src/seals.ts:185)  
   Ownership is checked only for the requested package. The returned segment contains **every global event** between its first event and the covering head, including unrelated subjects, actors, and `data`. Downloading an authorized package’s proof therefore exports other work’s information without checking its organization or effective lane. **Fix:** authorize every disclosed component and refuse mixed-scope exports until a privacy-preserving proof format exists. Add interleaved organization and lane tests.

2. **[P1] The “self contained” checker does not authenticate the seal.** [seals.ts:210](/home/flyfission/worktrees/control-rod-p5records/services/api/src/seals.ts:210)  
   `verifyInclusion` compares only the tail sequence and digest with the supplied seal. It ignores the assertion, signed subject, signer, organization, and challenge. A fabricated chain with a matching fabricated seal passes. The download also lacks the retained public key and verification context needed to authenticate it independently; the server’s earlier `verifyRecords` call does not authenticate a subsequently modified download. **Fix:** verify the seal’s reconstructed subject and WebAuthn assertion using retained credential evidence and an independently trusted anchor; distinguish link consistency from authenticated inclusion.

3. **[P1] Package identity and event completeness are unauthenticated.** [seals.ts:207](/home/flyfission/worktrees/control-rod-p5records/services/api/src/seals.ts:207)  
   The checker merely ensures caller-supplied sequence numbers occur in the segment. It never uses `package_id`, checks event subjects, or authenticates run-to-package membership. Relabeling a valid bundle to another package, setting `events: []`, or moving an earlier package event into the anchor all pass—even while retaining a genuine covering seal. **Fix:** derive the event set from authenticated package/run associations and validate its completeness through the sealed head. A concrete initial implementation can include the complete prefix from genesis plus committed run ownership; an arbitrary anchor cannot establish that no earlier package events were omitted.

4. **[P2] Retained keys are accepted without checking their historical authorization.** [seals.ts:94](/home/flyfission/worktrees/control-rod-p5records/services/api/src/seals.ts:94)  
   The verifier joins the credential to its signer but never reads credential history. Consequently, someone holding a revoked key and able to insert a forged seal row can create a fresh signature that is reported as valid. Preserving old signatures after revocation is correct; accepting signatures recorded after revocation is a different property. **Fix:** bind each seal’s complete digest and credential version to its recording event, then check enrollment and revocation history at that event’s position. Do not rely solely on signer-controlled `sealed_at`. Test both valid historical seals and forged post-revocation seals.

5. **[P2] Package verification discards a known global-chain failure.** [seals.ts:181](/home/flyfission/worktrees/control-rod-p5records/services/api/src/seals.ts:181), [app.ts:554](/home/flyfission/worktrees/control-rod-p5records/services/api/src/app.ts:554)  
   `inclusionProof` obtains the global verification report but returns none of its chain status. If corruption precedes the segment’s anchor, the local segment can still pass and the endpoint returns `check.ok: true`. This omits specification 11.6’s required **global chain verification plus inclusion proof**. **Fix:** return both results and make the overall package verification fail when the global chain fails, while separately describing any locally consistent segment.

6. **[P2] Verification reads can describe different database states.** [seals.ts:119](/home/flyfission/worktrees/control-rod-p5records/services/api/src/seals.ts:119)  
   Chain verification, seal selection, head lookup, and segment extraction run as separate pool queries. Concurrent writes can introduce a seal whose head exceeds the chain count already checked, yielding an incorrect unsealed suffix, or add package events after the event list was captured. **Fix:** run each complete verification/proof operation through the existing repeatable-read `readTx`, passing that same transaction through all helpers. Add a concurrency regression test.

7. **[P2] Successful sealing claims coverage through the refreshed head.** [Records.tsx:202](/home/flyfission/worktrees/control-rod-p5records/apps/web/src/pages/Records.tsx:202)  
   Success invalidates `records-head`, then renders “Sealed through entry” using that query’s latest value. The seal itself appends events, so the refreshed head advances beyond the signed head even without other activity. This violates N-4 and falsely implies those new events are sealed. **Fix:** render the returned seal’s `payload.head_seq`; test a head that advances after signing.
