# ADR 0023: Cast each role from a signed sheet, informed by scripted trials

- Status: Proposed (awaiting owner review)
- Date: 2026-11-16 (revised 2026-11-18 after the first cross-vendor review)
- Amends: the multi-provider design plan's non-goal "an editable strengths matrix, and any learning loop". The owner chose to amend it for every role, with checker guardrails, on 2026-11-18 (spec section 15, C-1); the ADR stays Proposed until the owner accepts it. This is an amendment, not a reading that fits inside the non-goal.

## Context
Control Rod runs a handful of agent CLIs, each able to launch several models. Today the author runtime is picked by a fixed order (`pickRuntime`: claude, codex, fake), with the CLI build pinned per runtime and role, and the checker is picked by another fixed order (`pickChecker`: codex, claude, fake) that excludes the author's runtime unless the owner signed an override. The owner wants the best available model for each job, with separate job sets for Software and Capital Projects modes. Models differ by duty: originating, checking, refuting, driving tools such as CAD and solvers, extracting from documents, planning, summarizing.

The multi-provider plan cut an editable strengths matrix and any learning loop, because a live, self-adjusting choice of checker invites shopping for a pass and cannot be audited. A sheet ordered from trial results is a strengths matrix, and reordering it is a loop with a person in it; this ADR asks to amend the cut on those terms.

## Decision
1. Each pack has a catalog of roles; each role has one **duty** and a domain agent spec (instructions, tools, rules, inputs and their modalities, outputs, sandbox profile, lane floor).
2. A passkey-signed, versioned **casting sheet** per pack lists, per role, grade and lane, an ordered list of candidates (harness, model, effort, required tier). There is one sheet per organization and pack; signing needs `policy` authority covering every grade a change touches. The sheet version in force is fixed into a package revision's signed policy at release, and every run of that revision uses it. The control plane takes the first candidate that passes admission, the runtime pin, the sandbox network policy, provider separation, the local-model rule and the tier floor; budget and quota hold the run on that candidate and never move it down the list. Version zero reproduces today's choices.
3. Trial results inform the owner's order through **role trials**: frozen, owner-held task sets run through the daemon as production runs are, scored by an approved script in a separate process the candidate cannot write to, with recorded inputs, outputs and digests bound to the run's attestation.
4. Nothing changes a cast except a newly signed sheet. Trial and production results are reported; they are never applied automatically. Sheet proposals are generated by a script from trial results. First-pass acceptance, sticky-fail counts and finding dispositions are diagnostic only for check and refute roles; only canaries and operational signals move a checker or refuter.
5. Specialists compose between runs in the control plane, never as subagents inside a counted run.

## Conditions
- Casting is a preference. Provider separation, the tier floor and the local-model rule stay kernel rules on attested facts; the kernel resolves tier from the signed registry on the attested identity, not from the sheet. A sheet cannot override them.
- Sticky fails stay keyed on the deliverable; no recast, re-claim or new sheet clears one. The owner's signed independence override stays outside the sheet.
- Provenance needs positive evidence. A run whose observed models are missing, empty or differ from its cast has unknown provenance; it cannot count as a check, and a check of an author or consult run with unknown provenance is held.
- In a flow, a checker is separate from every node whose output reached the deliverable it judges, by attested lineage; incomplete lineage means the check cannot count.
- No score is typed by a model (AGENTS rule 5). The record format rejects a score without scorer, answer key and attestation bindings.
- Capital Projects methods, alternates, references, inputs and tolerances come from a qualified domain owner; scripts take parameters by reference to controlled inputs, and a deterministic check rejects unlisted numeric literals. Trial items and reference results come from a qualified domain owner.
- New separation rules (by duty, by lineage, across a flow) are kernel and policy changes and need the owner's signature.
- No sheet other than version zero is signed before model provenance per cast is attested (C3), and none is used for counted checks before M6 and M9.
- Version zero keeps today's `default` model and so counts checks only as far as today; the registry refuses `default`, so counted checks rely on a sheet only after C3 replaces it with explicit registered ids. Until C6, a check counts under a non-zero sheet only where the deliverable's lineage is one attested author run.
- Exactly one sheet row applies per role, grade and lane, by a fixed precedence (exact grade and lane, then exact grade, then exact lane, then `any`); duplicate rows are refused at signing.
- The model is set only through the flag the adapter passes and the attestation parser reads (`--model` for Claude Code, `-m` for Codex today). Effort is added per CLI only after a flag is shown to work headless as a counted argument.
- Trial runs are their own job kind: they cannot claim or move a package, check a deliverable or count toward a quorum. Hidden tests and answer keys never enter the candidate's workspace.
- Review panel seats remain the recipients the person confirmed; a sheet may only propose defaults before confirmation.
- Consults are separate print-mode runs queued from a signed flow; the asking run has ended before their output exists.
- From the first sheet other than version zero (version zero keeps today's claim behavior, for parity), for check and refute roles a pin or installed-version mismatch holds the run (D-1); a daemon claims only if it offers every candidate ranked above the one it would run (D-2); a recheck after a fail goes to the checker that recorded it unless it lost qualification or the owner signs a reason (D-3).
- The signed M9 list is the checker baseline; reorders and additions need canary results meeting the D-4 bar.
- Engineering tools run only in a Control Rod tool runner between one-shot rounds, never inside the agent's sandbox for counted work (C-9).

## Alternatives considered
- **Keep the fixed order and pin by hand.** Simple, but extends badly past two harnesses and rests on no evidence.
- **A learned router that picks per task.** Rejected: unauditable, invites pass shopping, and conflicts with sticky fails.
- **Public benchmark scores.** Rejected as the basis: they measure other tasks, may be in training data, and come from vendors.
- **Adopt an outside agent specification.** Deferred: our ontology already holds the parts; license and fit unchecked.

## Consequences
- Easier: adding a harness or model becomes a qualification, a trial and a signed diff, not a code change. Each desk can say why it holds its model.
- Harder: trial sets must be built, kept private and fresh, and rerun for every compared candidate on rotation; Capital Projects trials need domain owners.
- Given up: any automatic improvement between signed sheets.
- Accepted: a person-mediated loop from evidence to the sheet, which the multi-provider plan had cut.
