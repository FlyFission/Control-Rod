# Software quality assurance for Control Rod (draft)

Control Rod is built so a customer's QA program can qualify it as quality-affecting software. The package is a byproduct of how the code is written.

## Package

| Item | Where it lives |
| --- | --- |
| Software quality assurance plan | This file, expanded in Phase 1 |
| Requirements specification | `requirements.sdoc` (StrictDoc), one ID per requirement |
| Design description | `docs/adr/` and the architecture documents |
| Verification and validation plan, test plans and reports | `docs/sqa/vv-plan.md` (Phase 1) and CI test reports |
| Traceability matrix | Generated by CI from requirement IDs cited in specs, code and tests |
| Configuration management | Git, signed commits and releases, change records in `.nuclear/changes/` |
| Problem reporting and corrective action | Tracked issues and security advisories |
| Release records | Signed, with SBOM, provenance, test results and open problems |

## Grading

The kernel carries the highest rigor: full requirement coverage, property and mutation testing, fuzzing and independent review. The control plane, daemon and sandbox integration are standard. Interfaces for people are lighter.

## Requirement IDs

`REQ-<AREA>-<NNN>`, where AREA is KRN (kernel), EVD (evidence), SBX (sandbox), API, DMN (daemon), SDK, or UI. Code and tests cite IDs in comments or test names. Standards text is never copied into requirements; requirements cite clause numbers only.
