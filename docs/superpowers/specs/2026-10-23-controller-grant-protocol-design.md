# Controller-backed preparation grant protocol

Status: implemented controller slice; final code review and publication evidence tracked in the execution ledger. Parent: runtime-confinement and preparation-file-broker specifications. All native preparation dispatch remains held; no policy/kernel activation is included.

## Decision question

Can the controller authorize exact file-capability operations across a remote broker without stale grants, blocked stop requests, replay escalation or treating reported hashes as retained artifacts?

The existing synchronous Authority callback is an in-process synchronization contract. A network adapter must not hold a database lock across filesystem/model I/O, nor implement it as fetch-and-trust. The distributed contract instead makes callback I/O provisional: begin admits a bounded single-use intent; finalize revalidates authoritative state and records/adopts the result in one bounded transaction. No bytes or receipt reach the model before successful finalize acknowledgment. An operation linearizes at controller finalization: an already-finalized original response can arrive after stop. Audit proves authorization/admission, not model consumption; stopping cannot recall delivered or already-authorized in-flight bytes.

## Domain and activation boundaries

Use the existing Run lifecycle and package/preparation heads, not a shadow preparation-session lifecycle. Add preparer values to the additive RunRole contract only after legacy claim/launcher paths explicitly refuse unsupported roles. No production code creates or claims preparer runs in this slice. Tests may seed fully schema-valid preparer runs as fixtures. No public grant-issuance route is added. Internal grant issuance is a mandatory future approved-runtime coordinator seam, not a replacement for kernel/policy authorization.

This slice implements controller record/storage and begin/finalize authority, with inactive dispatch. The Go distributed adapter/native transport is subsequent integration. Its existing callback documentation must be reconciled before connecting it; the current in-process provider contract must never silently become an optimistic fetch.

## Records and custody

TypeSpec remains the source of all serialized records: preparation role, immutable grant scope/capabilities, operation intent, permit, finalization request and receipt. Scope binds grant/run/package/preparation IDs, package/preparation revisions, complete preparation content digest, full stored package digest, role, lane, run claim identity and the nonextendable lease deadline. Pin exact retained input IDs/relative paths/raw SHA-256/length and fixed proposal basename. The first slice issues requirements-preparer grants only and projects the current preparation snapshot plus original capture/attachment DB bytes. It does not grant external repository/document/policy/package-dependency contents or issue technical-preparer grants. Referenced external basis is metadata, not a claim of observed external freshness. Future providers require an explicit capability/projection revision. The controller retains actual granted bytes at issuance. Model text cannot nominate host paths, source digests, IDs, role/lane, budgets or a grant.

Use independent random per-grant and per-use secrets, store hashes only and never emit secrets into events, logs or receipts. Grant issuance returns its token only to the trusted supervisor. Broker endpoints accept the narrow grant token, not ambient browser sessions or the general daemon credential. Grant record inspection/output history belongs to a separately authenticated future owner path; it is not a bypass for stopped agents.

## Begin/finalize semantics

- Begin takes a grant token and a closed intent: inspect, read-input with one assigned input ID, or write-proposal. It checks the current run is running, role and claim identity match, stop is absent, lease not expired, package/preparation/full content/basis still current, and the grant not revoked. It returns an intent-bound permit with a fresh use secret, deadline capped by the original grant and actual run lease, and the exact immutable grant projection.
- No database transaction or lock remains open while the broker performs file I/O. Package → preparation head → run → original capture/attachment → grant → use → event locks are taken in bounded server transactions. Grant transactions use PostgreSQL 17+ with a local one-second lock timeout, four-second SQL statement/idle limits and a server-enforced five-second total transaction timeout as resource ceilings. Audit acquisition failure rolls back and relinquishes package/run locks; no claim is made that stop can commit during a global database/audit outage. External filesystem/Git observation is excluded from this initial DB-only input projection; future observation must occur outside locks with deterministic dependency-lock ordering and honest observation timestamps, not a filesystem-wide freshness claim.
- Finalize verifies both secrets, permit/intent/claim identity and current authoritative fences again. Read results must match the controller-retained input digest/length. Inspect accepts no artifact or audit claims. Write finalization must carry the actual bounded canonical-base64 proposal bytes, not only a client-reported hash; the controller computes and retains the admitted artifact.
- Finalize records immutable result/receipt and audit once. A unique grant-scoped proposal slot admits one proposal even when two distinct write permits race; the loser refuses and exact winning retries return the original receipt. Exact retries use a request digest and return the same receipt only while authority remains current; altered replays refuse. A completed operation does not create a reusable read authorization after stop, revocation, revision change or expiry. Historical owner receipts are distinct from usable agent authorization.
- Unknown token/ID combinations refuse generically. Wrong operation/input/role/lane, duplicate JSON keys, malformed base64, excess bytes and unrecognized fields fail closed. Proposal content is untrusted data and never auto-applies requirements, resolves blockers or performs human actions.
- Use the database wall clock, not transaction-start now(), for deadlines. Recheck after potentially blocking audit locks. A deferred commit-time constraint checks permit/grant/run deadlines and stop state so waiting to commit cannot silently pass an expired authorization. Every successful begin/finalize acknowledgment, including SELECT-like exact receipt replays, inserts a transaction-end guard; no replay skips deadline enforcement. Lock protected state through commit. A network timeout has an ambiguous outcome; no client may infer success from it. Exact finalize retries resolve it subject to current authority. A committed controller proposal/receipt survives local cleanup and lost acknowledgment. If authority later expires, denial to the agent means unknown outcome to that agent, never proof the operation did not commit; retained owner custody remains authoritative.

## Required adversarial evidence before integration

Stop/revoke or edit between begin/finalize must refuse finalization; stop must not wait on a pending remote callback. Original lease extensions cannot revive an old grant. Wrong secrets, cross-grant/use substitution, role confusion, unknown-role legacy dispatch, replay after stop, altered replay, missing/tampered source bytes, claim turnover, delayed audit/commit expiry and oversized/ambiguous payloads must have real PostgreSQL/HTTP regressions. Check audit/secret absence and one retained artifact/receipt on exact retry. Existing manual confirmation/release/acceptance behavior must remain unchanged.

Runtime filesystem/credential/model egress, prompt-injection output semantics, safe artifact rendering and actual native delegation remain uncertain until separately tested. Keep assistance off; no active policy/red-team/CI or kernel decision changes are authorized by this design. A scoped activation authorization is still required.

## Bounded retention and abandonment

At most one grant is issued per run, at most two pending permits exist per grant, one proposal slot exists per grant, and every begin/finalize response consumes a finite grant operation budget (initial resource budget 64 responses, including exact retries). Each input/proposal stays within the existing controlled-source byte ceiling; total retained inputs use the existing aggregate source budget. The authenticated agent cannot choose or increase limits. Lost begin replies strand an opaque pending use until expiry: no secret is recoverable from its stored hash, no unsafe recovery/reissue is offered, and the attempt may require an owner stop/new approved run. Records remain bounded per grant; global operational retention and trusted coordinator issuance quotas remain a deployment gate.

Legacy claim/start/heartbeat/completion/requeue/override paths require explicitly supported role/body agreement; owner stop and expiry retirement remain available. New serialized role values cannot activate old author/checker fallbacks.

## Input layout and runtime floor

Grant input paths are basenames relative to a dedicated input root, not the overall workspace; proposal output belongs to a distinct sibling root. The transport must materialize and verify exactly those bytes before opening the Go broker. Grant assignment also pins baseline/runtime/round; changing that configuration invalidates pending authority even if the claim hash is unchanged. PostgreSQL 17+ is required only for the new grant protocol's total transaction timeout; unsupported servers refuse grant operations instead of weakening the budget. The test harness uses a qualifying host server or pinned embedded PG17. Fatal deadline failures discard the client and preserve the original error. Receipt timestamps are database decision times, not exact commit or model-delivery timestamps.

## Disclosure activation prerequisite

An unconfirmed draft package’s `data_lane` is an input label, not evidence of owner-authorized disclosure. The future approved coordinator must establish trusted disclosure classification and a permitted runtime profile before creating or issuing a preparer attempt. This slice derives scope only from an existing run and exposes no public issuance or preparer dispatch; synthetic SQL fixtures do not prove that missing authorization path. Native transport must not expose the returned token or retained bytes until that gate and the process/credential/egress boundary are established.
